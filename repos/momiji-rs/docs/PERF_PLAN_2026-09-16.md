## Part A — improvement plan

### A0. Land the gate first (blocking)

Part B is a prerequisite for Part A, not a follow-up. The single largest item
in the audit is *recovering a regression that CI merged two days earlier*.
Shipping A1 before the gate exists means the same class of loss can be
re-introduced by the next PR and nobody will know. Part B is also cheap: the
whole benchmark fix is four lines plus two `Cargo.toml` keys.

### A1. `dep-no-eager-construction` — the only general-path lever

**Win: −14.3% instructions `[measured]`** (153.4M → 131.5M), wall −15.9 to
−21.1%, peak footprint 28.36 → 25.15 MB. Prototyped, byte-verified over
~30,500 A/B pairs with `spec/check_baseline.py` delta +0 and 803 tests passing.

*What it does.* Gate before constructing. `deprecations_seen` becomes an
`FxHashSet`; a `dep_memo` fingerprint-and-verify cache answers a repeated call
site without re-deriving anything; `deprecations_live()` is hoisted above the
work; the gates move ahead of `is_builtin` and `color_function_suggestions`.
Touches `src/eval/mod.rs`, `src/builtins/mod.rs`, `src/builtins/color/deprecate.rs`.

*Where the win actually comes from.* The memo is ~11.1 of the 14.3 points; the
name gate is ~3.2 `[measured]`. A "cheap subset" that only adds the gates
captures ~22% of the win. Do not take the subset.

*Honest framing.* This is not a new optimisation. It is recovery of a
regression merged on 2026-09-15 by PR #39 `465c592` (+15.4M) and PR #40
`da6d073` (+15.1M). Say that in the commit message, and be careful with the
denominator: the lever recovers **21.92M**, which is **91% of the deprecation
feature tax** as bracketed by the corpus migration (23.96M) but only **~72% of
the +30.5M those two merges added**. Do not quote 91% against the regression.

*Known cost.* On deprecation-free input the patch measures **+0.136%**
`[measured]` — the memo costs a little where there is nothing to memoise. That
is an acceptable trade and it should be stated, not hidden.

*Ship conditions, all mandatory.*
1. A `debug_assert` verify path behind the fingerprint key. The key is a hash;
   a collision would silently drop a warning, which is a parity break.
2. A size cap on `dep_memo`, so a pathological sheet cannot grow it unbounded.
3. A drift guard in the shape of T1.3: an equivalence test asserting
   `deprecates()` / `suggestions()` agree with the real deprecation tables.
   Without it the gate and the table can diverge and the gate wins.
4. Drop the throwaway `examples/embed_probe.rs`.
5. A comment explaining the `--verbose` bypass. The footer at
   `src/eval/mod.rs:2010` already prints "Run in verbose mode to see all
   warnings." although no such flag exists.
6. `spec/check_baseline.py` delta +0 and `cargo test --release` green, both
   re-run on the final patch rather than quoted from the prototype.

*Risk: medium.* It touches the diagnostics path that dart-sass parity depends
on. It also has the strongest evidence in the audit.

*Sequencing.* One atomic commit. It is one behavioural change with one
measurement.

**Landed in #50.** The cumulative −15.29% in Current state is very nearly this
lever alone: of everything merged since the tree of record, A1 is the only change
that touches the single-file general path.

### A2. `extend-store-index-and-ext-breaks-hoist` — the `@extend` carve-out

**Win: 0.00% on the general path `[measured]`. −13.6% / −29.6% / −32.5%
`[measured]` on bootstrap / tabler / forem, with 40–88% peak-memory
reductions.**

This is worth landing precisely because it is invisible on `large.scss`. It is

compiles an `@extend`-heavy sheet. Land it *after* the gate acquires an
`@extend` corpus (Part B, B4), otherwise the win is unprotected the moment it
lands.

**Implementation constraint — the obvious recipe is unsound.** The audit's §4.3
refuted the extracted version of hunk (1): a plan-level `ext_breaks` **map**

deep dive's substitute instead: an **`FxHashSet` of only the true-flagged
extenders**. Land hunks (1) and (2) plus the `Cow` change together. Sub-lever
(3), the target-simple index, is **unbuilt and unmeasured** — do not land it on
this evidence.

**Landed in #53**, byte-identical output. Its win stays invisible on
`large.scss` by construction, which is exactly what `extend_heavy_with_url_silent`
(#51) exists to watch.

*Caveat that bounds the claim.* It fixes the constant, not the exponent
(~1.79→1.90 growth before, ~1.37→1.60 after). `extend_simple` still measures
226.55 ms / 3,362M instructions / 1,525.8 MB peak from ~45 KB of source. The
`@extend` asymptote remains an open problem, listed under A5.

## Part B — the perf gate

### B0. A gate already exists, and it reports nothing anyone can act on

`.github/workflows/codspeed.yml` runs on push to master/main, on every
`pull_request`, and on `workflow_dispatch`: `cargo codspeed build` then
`CodSpeedHQ/action@v4` with `mode: simulation`. So the infrastructure is
present. A 19% regression got through anyway. The decisive reason is the
simplest one — **there is no threshold, so no benchmark result has ever blocked
a merge** — and on top of that the benchmark measures a materially different
program than the one that ships, in two ways, both now measured rather than
inferred. (A third defect was claimed here and withdrawn; the retraction is
kept below rather than deleted, because it is the same failure mode this Part
is about.)

Measured 2026-09-16 with `cargo codspeed run -m walltime`, fastest / median ms,
`large_expanded` only:

| Benchmark configuration | macOS / arm64 | Linux / x86_64 |
| --- | --- | --- |
| as it exists in the repo today (no arena, no URL) | 13.78 / 14.63 | 13.14 / 13.89 |
| `+ #[global_allocator]` | 8.195 / 8.467 | 10.30 / 11.18 |
| `+ #[global_allocator] + with_url` | 9.478 / 9.810 | 11.29 / 12.10 |
| `+ #[global_allocator] + with_url` + no-op warn handler | 9.408 / 9.840 | 11.27 / 12.06 |
| CLI, shipped config, same machine, same hour | 9.794 | 12.278 |

**Defect 1 — the benchmark never installs the arena.** `src/main.rs:40`
installs `ScopedAlloc` as `#[global_allocator]`; `benches/compile.rs` does not.
Every CodSpeed number ever recorded measured sasso against the system malloc.
The error is **−41% on macOS and −22% on Linux** `[measured]`, and it is not
merely a constant offset: it *inverts the cross-platform ranking*. On
`nesting`, without the arena macOS reads 17.16 µs against Linux's 14.27 µs;
with the arena macOS reads 9.25 µs against Linux's 9.76 µs. A benchmark that
reorders platforms is not measuring the product.

**Defect 2 — no benchmark supplies a URL, so the diagnostics half that runs
behind the guard is switched off.**
`diag_enabled()` is `!self.options.source.is_empty()` (`src/eval/mod.rs:1669`),
and `src/lib.rs:560-563` only populates `diag_source` when `options.url` is
`Some`. All five benches use `Options::default()`. Supplying a URL costs
**+15.7% on macOS and +9.6% on Linux** `[measured]`.

Be precise about what that hides, because "the benchmark sees none of the
regression" would be too strong. The guard is inside `emit_deprecation`
(`src/eval/mod.rs:1935`), and both callers do real work *ahead* of it:
`emit_call_deprecations` canonicalises the name, may allocate a `replace`,
looks up `global_builtin_replacement` and constructs the `Deprecation`, while
`emit_color_function_deprecation` runs `is_builtin`, builds
`color_function_suggestions`, and `format!`s the qualified name — all before
the early return. So a no-URL benchmark **does** price the construction half.
The audit's own no-URL embedder arm records lever A1 at **−8.39%** there,
against −14.29% with a URL.

What the missing URL hides is the rest: the dedup insert, the per-id cap, the
`quietDeps` filtering, the rendering and the footer. On this corpus that is the
15.7% above, and it is invisible today. The regression was therefore *partly*
detectable by the existing benchmark and nobody was watching, because there is
no threshold — and the URL-gated half was not detectable at all. Both halves of
that need fixing, which is why B1 and B2 are separate steps.

**There is no third defect, and an earlier draft of this document invented
one.** It claimed `[profile.bench]` inherits neither `lto` nor `codegen-units`
from `[profile.release]`, worth ~1.7%. That is **wrong**, retracted 2026-09-16.
`cargo build --profile bench --lib -v` passes rustc `-C opt-level=3 -C
linker-plugin-lto -C codegen-units=1`: Cargo's `bench` profile inherits
`release`, and `linker-plugin-lto` is how `lto = "thin"` reaches an rlib.
Re-running it under `CARGO_PROFILE_RELEASE_LTO=off
CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16` flips the bench build to `lto=off
codegen-units=16`, which demonstrates the inheritance instead of assuming it
`[measured]`. The ~1.7% once attributed to the profile (13.78/14.63 against
13.55/14.08 ms) was cross-window noise — exactly the sub-1% trap §1 of the
audit warns about, walked into by this document's own author. `Cargo.toml`
needs no change, and the mistake is left recorded here because it is the same
class of error the whole of Part B exists to prevent.

Two further facts the experiment turned up, both needed to write the fix:

- **stderr is not the cost.** A no-op warn handler measures the same as
  printing (9.408 vs 9.478 fastest, 9.840 vs 9.810 median). So the gate can
  keep diagnostics hot *and* stay quiet. The ~16% is bookkeeping, not I/O —
  a third independent confirmation of the audit's 16–17% figure.
- **`WarnHandler` is `Rc<dyn Fn…>`, which is not `Sync`.** divan requires a
  `Sync` closure, so the handler must be constructed *inside* the benched
  closure. One `Rc::new` per iteration is noise at 9 ms.

With both defects fixed, the benchmark reads 9.478 ms against the CLI's
9.794 ms on the same machine in the same hour — within 3.2%. Before the fix it
read 13.78 ms against that same CLI: 41% *slow*, not fast. The direction is
worth stating plainly, because a wrong gate is usually assumed to flatter its
subject and this one did the opposite. As an absolute number the old benchmark
was pessimistic. Its failure was not optimism but subject: it measured a
different program from the one that ships, and was blind to the single region
that regressed. A pessimistic gate is no more useful than an optimistic one.

### B1. Fix the benchmark (do this first, alone, in its own commit)

Land it as a **no-behaviour-change commit before A1**, so the gate's history
contains a clean pre-A1 baseline to compare against.

1. Add to `benches/compile.rs`:
   ```rust
   #[global_allocator]
   static GLOBAL: sasso::ScopedAlloc = sasso::ScopedAlloc;
   ```
2. Add a URL-bearing variant of the large workload with a no-op warn handler,
   so the diagnostics path is measured without stderr noise. The name matches
   the appendix's silent arm, because that is the arm to land: the appendix's
   printing `large_expanded_with_url` arm exists only to prove stderr is not
   the cost (9.478 against 9.408 fastest — the same within noise), and a
   benchmark that writes to stderr has no business in CI.
   ```rust
   #[divan::bench]
   fn large_expanded_with_url_silent(bencher: Bencher<'_, '_>) {
       bencher.bench(|| {
           // WarnHandler is an Rc, which is not Sync, so it cannot be hoisted.
           let sink: sasso::WarnHandler = std::rc::Rc::new(|_ev: &sasso::WarnEvent<'_>| {});
           let opts = Options::default().with_url("large.scss").with_warn_handler(sink);
           compile(black_box(LARGE), &opts).unwrap()
       });
   }
   ```
   Keep the existing no-URL `large_expanded` too. The **pair** is the useful
   signal: their ratio is the diagnostics surcharge, and watching that ratio
   would have flagged PR #39 and PR #40 directly.

That is the whole of B1 — two steps, not three. `Cargo.toml` is not touched,
per the retraction above.

### B2. Give the gate teeth

Today the workflow reports and nothing blocks. Three changes:

1. **Set a threshold.** CodSpeed's default noise handling is not a gate.
   Configure a regression threshold and, `[estimated]` from the spread
   observed here, start at **5%** on the large workloads. Simulation mode
   counts instructions rather than wall time, so it is far quieter than the
   walltime numbers in B0 — tighten toward 2–3% once a few weeks of history
   show the real band. Do not set it from wall-clock variance.

   *Status 2026-09-17: still open, and the last outstanding item in this file.*
   The evidence gathered since now favours starting at **2–3%** rather than 5%.
   Instruction counts reproduced across two independently built trees to 0.003%
   on an untouched control (133.849M vs 133.844M), and the smallest delta this
   plan cares about keeping — A3's, on the Linux instruction axis — is only
   0.9–1.2%. A 5% band would let that whole lever regress silently.
2. **Make the check required** on the master branch protection rule. A
   reported-but-not-required check is a dashboard, not a gate.

   Neither of those two is a code change. `.github/` contains only `workflows/`
   — there is no ruleset or settings-as-code in this repo (verified
   2026-09-16) — so the threshold lives in the CodSpeed project settings and
   the required-check flag in GitHub branch protection. Both must be done by
   hand, and **both must wait until A1 has landed**: turning a threshold on
   while master still carries the PR #39 / #40 regression locks that regressed
   number in as the baseline.

   *Status of item 2, 2026-09-17: done.* master had no protection rule and no
   ruleset at all (verified before the change). It now carries a classic
   branch-protection rule requiring five contexts — `fmt · clippy · test`,
   `dart-sass parity`, `sass-spec ratchet`, `native addon (build + parity +
   test)` and `CodSpeed Performance Analysis` — with `strict: false`, no required
   reviews, and admin enforcement left off. The four correctness checks block a
   red merge as of today; the CodSpeed context blocks only a *failed run* until
   item 1 gives it a threshold to fail on. The baseline-locking constraint was
   honoured: A1 landed in #50 first.
3. **Keep simulation mode.** It is valgrind-based and Linux-only, which is why
   it cannot run on this fleet's Macs — and it is also the reason it is the
   right choice for CI. Instruction counts do not care about a noisy runner.
   The walltime numbers in this document are for local A/B work only.

### B3. Where instrumented measurement runs

- **CI, per PR: `ubuntu-latest` + simulation mode.** Already configured. Cheap

- **Local A/B, macOS: `/usr/bin/time -l` on the CLI with `--loop 20` and

### D2. What an allocation is worth

Every batch measured its own price — instructions saved divided by allocations
removed, on the corpus the batch targeted. Across the fifteen landed batches
that price ranged from **~17 to ~287 instructions per allocation, median ~103**.

The spread is the whole lesson, and it is not about the allocator. A compile
runs under the scoped bump arena (`src/arena.rs`), so an allocation *inside* a
compile is a pointer bump and its free is a no-op — worth on the order of ten
instructions, not a hundred. What the expensive batches removed was the **work
wrapped around** the allocation:

- The steepest, batch 15 (#106, ~287), deleted `format!` calls: a `calc()` now
  serializes into the caller's buffer, so what disappeared was `core::fmt`
  dispatch, not `malloc`.
- The cheapest, ~17, removed a bump and nothing else.

So allocation count was a good *search index* for wasted work and a bad *unit
of account*. Read D3 before treating a future allocation win as a win.

### D3. The mechanism that closed the campaign (measured, not shipped)

Batch 16 built a list literal's `Rc<[Value]>` in ONE allocation instead of two:
a pooled scratch `Vec<Value>` drained straight into the `Rc`
(`buf.drain(..).collect()` — `Drain` reports an exact length, so `Rc<[T]>`'s
`FromIterator` allocates once), plus four `vec![a, b].into()` sites rewritten as
`IntoIterator::into_iter([a, b]).collect()`. It passed every gate and removed
allocations as designed: `large.scss` −6.42%, `units.scss` −3.60%,
`colors.scss` −2.95%, `calc.scss` −2.42%, `modcalls.scss` −1.45%.

It also made every one of those corpora **slower**:

| Corpus | instructions | Corpus | instructions |
| --- | --- | --- | --- |
| `colors.scss` | +0.611% | `modcalls.scss` | +0.243% |
| `large.scss` | +0.482% | `handwritten` | +0.205% |
| `calc.scss` | +0.477% | `modular/entry_01` | +0.163% |
| `units.scss` | +0.457% | `extend_heavy` | +0.013% |
| `use_graph/entry` | +0.255% | `wrap.scss` | +0.010% |

`longsel.scss` measured +0.000% — and it is one of exactly two corpora whose
allocation count the batch did not change, which is the tell: the regression
tracks the mechanism, not code layout. A bisect confirmed it. The pooled
list-literal arm alone measured +0.431% on `large.scss` and +0.604% on
`colors.scss`; the four two-element sites alone measured +0.051% on
`large.scss`, reproducible to within 9 instructions across rounds.

The physics: `Vec<T> → Rc<[T]>` costs two allocations and exactly one bulk
`memcpy`, while a drained collect costs one allocation and moves the elements
one at a time. A `Value` is 64 bytes and a stylesheet's lists are short, so the
element-wise path pays **+77 instructions per allocation it removes** on
`large.scss` (+61 for the two-element sites) — against a bump worth ten. A
one-allocation build with a bulk copy would need `Rc::new_uninit_slice`
(Rust 1.82, above the 1.74 MSRV) or `unsafe` outside `src/arena.rs`. Both are
barred, so the shape has no version that wins, and nothing was committed.

**Rule this leaves behind:** an allocation-count win ships only after the
marginal-instruction A/B agrees. The wins that keep paying delete a
`format!`/`String`, or a genuine copy — not a bump.

### E2. Widen the scoreboard: cycles, and what instructions cannot score

The claim put to this review: a cycles or cache-miss profile could be sharply
peaked where D4's instruction profile is flat, and if so that outranks every
code lever. **The claim is half right, and the half that is right is enough.**

What the evidence supports:

- `[measured, bench/perf_audit_2026-09-15.md:57-72]` the two axes already
  disagree inside this binary: emit is 3.3% of instructions but 5.1–6.4% of wall
  samples, because emit runs at IPC 2.58 against 4.39 for the whole compile. A
  1.7× IPC spread between regions of the same program on the same machine is
  established fact, not conjecture.
- `[measured]` 2026-09-18: `/usr/bin/time -l` prints `instructions retired`
  **and `cycles elapsed` on the line below it**. The metric-of-record recipe at
  `bench/perf_audit_2026-09-15.md:973-977` greps
  `instructions retired|peak memory|real` and throws the cycles line away.
  Marginal cycles and IPC have been one grep character away for the entire
  campaign.

What it does not support:

- Whole-program IPC is already 4.0–4.25 on arm64. A program retiring four
  instructions per cycle is not stalling much, which bounds total recoverable
  stall there to something small. The Linux arm at IPC 2.52 has more headroom,
  but part of the 1.7× cross-platform gap is **ISA and machine width, not
  stalls**: `[measured]` 2026-09-18, rustc 1.98.1 compiles the x86_64 target for
  `fxsr,sse,sse2` only — a 2003 baseline — against aarch64-apple-darwin's 28–29
  features. The appendix's "same work, differently issued" framing compares two
  differently-provisioned builds.
- The only region measured to be peaked (emit, 1.7×) is 3.3% of instructions.
  1.7× on 3.3% is ~2% of wall. That is not a hidden mountain.
- The appendix's own arm64 row mixes scales: 153.23M marginal ÷ 38.2M cycles is
  **IPC 4.01**, not the printed 4.25 (which is 162.4M naive ÷ 38.2M). The ratio
  survives; the cells do not reconcile. Restate the arm64 cycles as marginal
  before scoping anything against the cross-platform gap.

**So the reason to widen the scoreboard is not a hidden mountain. It is that
several surviving levers are instruction-for-locality trades whose *sign* the
current metric cannot determine**, and the fix costs one grep character:

| Lever | Why the instruction metric mis-scores it |
| --- | --- |
| shrink `Value` (E6 S-a) | trades stack moves for arena bumps and refcount RMWs; the win is bytes moved, a cycles quantity |
| number-format memo cache (E5 M-g) | adds ~34 KB of near-randomly-touched thread-local table; instructions can read −3% while wall reads flat |
| hot/cold split of `exec` (E6 S-d) | reads ~0.00% on instructions **by construction**; its entire effect is I-cache footprint |
| PGO, `target-cpu`, block layout | same — an entire lever class currently unscoreable and therefore unproposable |

**Do this first; it costs minutes, then an afternoon.**

1. ✅ **Done 2026-09-18.** Change the recipe's grep to take `cycles elapsed`.
   Report **(I_marginal, C_marginal, IPC)** as a triple for every arm of every
   A/B from here on. Cycles are load- and frequency-sensitive where instructions
   are not, so the interleaving discipline applies more strictly, not less — and
   the band says how much more. `[measured]` 2026-09-18, macOS / arm64, the same
   binary copied twice and run through four interleaved ABBA rounds at load ~8.6
   on 12 cores: **instructions ±0.03%** (per-round deltas −0.010 / +0.002 /
   −0.033 / −0.024%) against **cycles ±1.9%** (−1.27 / +1.90 / −1.00 / −1.39%,
   sign flipping every other round, which is what pure noise looks like). So the
   cycles band is **~60× wider than the instruction band**, and IPC inherits it
   (control spread 4.199–4.366). Practical rule: quote a cycles delta only above
   ~2%, or with the sign agreeing across every round, or from a quieter box.
   Re-establish the band whenever the machine's load regime changes; this one
   was taken under load, which is the pessimistic case.

   `[measured]` 2026-09-18, the same control-pair procedure on Linux / x86_64,
   idle (load 0.2 of 16 threads), 12 interleaved rounds instead of 4:
   **instructions 0.000%** — two copies of one binary agreed to three decimals
   of a million in every round, so on an idle Linux box one round is exact and
   the interleaving is belt-and-braces — against **cycles 0.14% and 0.59%** (two
   separate control pairs, taken in different windows) and **task-clock 0.7% to
   2.5%**. Three rules follow. Quote a Linux cycles delta above ~1% rather than
   macOS's ~2%; prefer the **paired per-round sign count** to the mean, since it
   is the statistic that separated a real 2.5% from a positional 0.6% in E2 step
   4; and do not quote task-clock at all — it is the widest of the three on both
   boxes and it disagreed with cycles twice. One caveat matters more than the
   widths: the interleave runs the arms forward at 60 loops and backward at 20,
   which places the first and last arm at **maximum positional separation inside
   the marginal subtraction**, so a control pair's spread is that positional
   bias and not thermal drift. Put the arm you expect to win *later* in the
   order and the bias works against you.
2. **Open the CodSpeed flame graph for master.**
   `[unverified — vendor docs, not read against the live UI]` CodSpeed's
   CPU-simulation instrument is described as an estimated-cycles cost model

**#12 cost more than "one script arg + baseline" and is worth far more than
"0% direct".** The estimate assumed a compressed run could be scored against
the expectations already in the suite. It cannot: sass-spec ships exactly one
`output.css` per case and dart-sass generated all of them in the default
`expanded` style. There is no compressed expectation anywhere in the tree
(`[read-from-code]` no `output-compressed`, no `:output_style` key), so
`--style=compressed` against `output.css` fails nearly every success case on
whitespace alone — `[measured]` 58 PASS of the 497 non-error cases in the first
600, i.e. the naive gate would ratchet a number that means nothing.

Scoring compressed output therefore needs a **second oracle**: the compressed
CSS a reference dart-sass emits for the same case. `spec/COMPRESSED_EXPECT.txt`
is that oracle — 11,766 lines, one per non-error non-skipped case, each a
12-hex-char sha256 of dart-sass 1.104.1's compressed output after the same
normalization the byte-exact comparison applies. `spec/gen_compressed.py`
generates it (reusing `run_spec.py`'s own case model and materialization, so the
oracle and the scorer cannot drift), and `run_spec.py --expect-file` scores
against it. Four decisions are load-bearing:

* **Digests, not text.** 777 KiB committed instead of several megabytes, and the
  file diffs one case per line.
* **Committed, not cached.** The gate then needs neither node nor the network:
  `python3 spec/check_baseline.py --style compressed` is as offline as the
  expanded one. An `actions/cache` miss would otherwise turn the gate into a
  20-minute dart-sass run.
* **A missing entry is `SKIP`, never `FAIL`.** A gap in the oracle must not read
  as a sasso regression. Reviewed on PR #142: that choice lets a truncated
  manifest drop cases out of the *denominator* instead, so the ratchet also
  refuses an `attempted` below the baseline's, and the manifest's `cases:`
  header must match its body. `[measured]` deleting 5 failing digests leaves
  `delta +0` and a pass% that *rises* to 88.26% — it now exits 1. A second
  review pass found the mirror image, which that check cannot see: if the
  eligible set *grows*, `attempted` returns to the baseline while the new cases
  go unscored. The ratchet now also requires the manifest to cover every case
  the run was eligible to score, with `reference_errors:` as the exact
  allowance. `[measured]` on a synthesised run of that shape the previous code
  printed `ratchet OK` and read the gap as **+5 passing**.
* **The ratchet refuses a stale oracle.** `check_baseline.py` exits 2 if the
  manifest's `dart_sass` header disagrees with `BASELINE_COMPRESSED.json` or its
  `spec_commit` disagrees with `SPEC_VERSION.txt` — verified by perturbing the
  header. `run_spec.py` separately exits 2 if the manifest's `style` header is
  not the `--style` being scored, since nothing about a digest says which style
  produced it. Without those, a pin bump or a dropped flag would silently score
  the wrong thing. Reviewed again on PR #142: all four headers are now
  *required*, not merely compared when present — a check that a deleted line
  switches off is not a check.

The manifest is reproducible: two independent generations from the same pins
produced a **byte-identical** digest body (`[measured]`, md5 of the file below
the header). That is what makes a regenerated file's diff readable as "upstream
changed these outputs" rather than as noise.

Error specs are excluded from the manifest entirely: their verdict is the exit
status, which is style-independent, so the compressed run scores them exactly as
the expanded one does — `error_expected` is 2,492 in both baselines, and the two
`attempted` counts agree at 14,258.

**Fixed 2026-09-19, the day after, with the gate as the scoreboard.** The
classification above had the right two families and the wrong rules; measuring
against the reference instead of guessing gave:

- **The colour channel units.** A `lab`/`lch`/`oklab`/`oklch` lightness is
  written as the channel's own stored number when compressed — the same digits
  for lab/lch (0–100) and the *unscaled* 0–1 value for oklab/oklch, so
  `oklab(1% 0 0)` becomes `oklab(.01 0 0)`, one byte longer. It is a fixed rule,
  not shortest-wins: `oklab(33.333333% …)` and `oklab(.33333333 …)` are the same
  length and dart writes the second. A hue drops `deg` everywhere, including the
  modern form of `hsl()`/`hwb()`. `[measured]` **+963 passing**.
- **The leading zero of a fraction**, which has three regimes, not one, because
  dart has two number writers. Sweeping `0.1` … `0.1234567891234` and their
  negations against dart-sass 1.104.1: a spelling shorter than `precision + 2` =
  12 characters goes to the direct writer, which tests for a literal `0.` prefix
  and so keeps the zero on `-0.5`; a longer one goes to `_writeRounded`, which
  drops the integer `0` for *either* sign once it actually has digits to round
  away (`-0.00123456789` → `-.0012345679`); and a long spelling with nothing to
  round passes through verbatim, keeping the zero even when positive
  (`0.0123456789`). sasso had only the first rule. `[measured]` **+433 passing**
  on top of the first fix.

Compressed passing goes **12,579 → 13,975** of 14,258 (88.22% → 98.02%);

**Two of those closed the same day, for +26.** An at-rule is not invisible when
its block writes nothing: dart's `_isInvisible` short-circuits on `CssAtRule`
deliberately — "because we don't know the semantics of unknown rules, we can't
guarantee that (for example) `@foo {}` isn't meaningful" — while `@media` and

**13,975 → 14,001** (98.20%), expanded still `+0`.

**The string-preservation lesson closed the next lever, 2026-09-20, for +8.**
A degenerate legacy colour (`hsl(0, 100%, calc(-infinity * 1%))`) was an
unquoted string here and a colour in dart, so its compressed spacing could not
change — the same shape as the `round()` fix, and the same fix: store the
infinity in the channel and let the serializer write it. `hsl()`/`hsla()` now
build a real colour (hue modulo 360, negative saturation floored at 0, NaN read
as 0, a degenerate alpha folded), and `color()` needed no special case once its
own string early-return went. Compressed passing **14,001 → 14,009** (98.25%),
expanded still `+0`.

What the fix cost was in the serializer, not the constructors: these colours are
OUT OF GAMUT, and probing that corner against the reference turned up three
divergences no spec case reaches. A computed out-of-gamut rgb colour — what
`color.mix()` returns — carried no space tag, so it never reached the rule that
writes such a colour through its hsl form (`rgb(NaN%, NaN%, NaN%)` against
dart's `hsl(0, 0%, 0%)`); that hsl form must null the hue when the saturation is
fuzzy-zero, as the compressed rgb-or-hsl choice already did, or an out-of-gamut
grey leaks `hsl(345, 0%, 100%)`; and `meta.inspect`, which skips the hsl form
and writes `rgb()`, used its own channel writer rather than the shared one, so a
non-integral channel kept its number where dart re-spells all three as
percentages (`rgb(510, 0, 127.5)` → `rgb(200%, 0%, 50%)`) and a non-finite one
reached the stylesheet as a bare `NaN`/`-Infinity` instead of `calc(NaN * 1%)`.
All fixed and pinned by tests; all `[measured]` against dart-sass 1.104.1 in
both styles.

One rule is measured and **not** fixed: dart converts a NaN channel to 0 when a
colour is CONSTRUCTED and not when one is CONVERTED, while `make_modern_in`
normalizes on every conversion. So `color.to-space(hsl(0, 100%,
calc(-infinity * 1%)), lab)` is `lab(0% 0 0)` here and
`lab(calc(NaN)% calc(NaN) calc(NaN))` in dart, and `color.channel()` of such a
converted channel reads 0 rather than `calc(NaN)`. Splitting construction from
conversion touches every conversion path in the colour module, including the
negative-zero rule that shares the same normalizer, for a corner no sass-spec
case reaches — so it is recorded here rather than attempted.

The same empty-at-rule rule had to be applied a second time, in the plain-CSS
evaluator: it builds its own output nodes, so a `.css` file reached through
`@use` dropped `.a {@foo {}}` in *both* styles. Its three body dispatchers also
had no arm for `@keyframes` or for a custom `@function`, dropping both outright
— `@media screen {@keyframes k {from {a: b}}}` came out empty, and the empty
`@media` then went too. Probing that path against the reference turned up
**five more divergences**, most of them fixed here. The first is not: its
first-level at-rule bubbling does not keep the at-rule's source position,
because dart splits the parent rule around it — `.k {a: b; @foo {x: y} c: d}` in
a loaded `.css` file is `.k{a:b}`, `@foo{.k{x:y}}`, `.k{c:d}` — while this path
emits the whole parent first and every bubbled at-rule after it. The synthesized
copy of the parent also carries no source lines, which is what the one-line
`.g { /* c */ }` join is decided on. `[measured]` against dart-sass 1.104.1,
expanded and compressed; the SCSS evaluator is byte-exact on all of these
shapes, so the fix is to make the plain-CSS path emit segments the way that one
does. No sass-spec case covers it, which is why neither gate moved.

The next two were about what a `@keyframes` **frame** is. Nothing inside a
frame bubbles in dart: `@keyframes k {from {@foo {a: b}}}` is
`@keyframes k{from{@foo{a:b}}}`, and
`@keyframes k {from {@keyframes j {to {a: b}}}}` keeps its frame. Both
evaluators hoisted any at-rule out of the frame instead, wrapping the frame
selector around its body (`@keyframes k{@foo{from{a:b}}}`) or losing the frame
outright when the child was another `@keyframes`; only `@media` and `@supports`
escaped it. The plain-CSS side is **fixed here** — the dispatcher that builds
frame bodies now reads them the way any deeper level is read, with no hoisting —
and so is a second frame divergence it turned up: a style rule inside a frame is
an error in dart's plain-CSS parser, `@keyframes k {from {.x {a: b}}}`, where
this evaluator produced output for it at every depth. Both evaluators now raise
that error from one place and point at the offending rule; dart underlines the
whole rule and we draw a single caret, since the AST keeps no end column for a
rule. The **SCSS** evaluator's own frame hoisting is unchanged and still open.

The fourth is what a frame's selector *is*: a list of keyframe **stops**, which
dart re-serializes joined with `", "`, not a selector list. The plain-CSS path
ran it through ordinary selector normalization, so `0%,\n50%` stayed on two
lines where dart writes `0%, 50%`, `+5%` gained a space as though `+` were a
sibling combinator, and `130E-1%` kept the marker's case. The `from`/`to`
keywords were verbatim on **both** paths, where dart lowercases them
(`FROM` -> `from`). Stop normalization is now one function both evaluators call,
and the plain-CSS frame path builds stops instead of selectors. What neither
path checks is the stop **grammar**, and that stays open: dart accepts only
`from`, `to` and `<number>%` in a frame, so `@keyframes k {foo {a: b}}` is
`Expected "to" or "from".`, `&` and `[a=b]` are `Expected number.` and `50 %` is
`expected "%".`, where both evaluators here emit the frame. Closing it means one
shared validator, three messages and a span per stop — the rule AST has one
position for the whole selector, so the caret would land on its start.

The last divergence is the SCSS evaluator's: a bubbled custom `@function` loses
the copy of the parent selectors that every other bubbled at-rule takes with it.
`.a {@function --f(--a) {result: 1}}` in an `.scss` entry is
`@function --f(--a){.a{result: 1 }}` in dart and `@function --f(--a){result: 1 }`
here, and dart keeps resolving selectors as it descends, so
`.a {.b {@function …}}` wraps `.a .b`. In a loaded `.css` file this was a
*different*, larger bug, and it is fixed here: neither rule-body dispatcher had
an arm for the statement, so the at-rule vanished whole. It now bubbles with the
parent copy at the first level and stays nested below it — where dart wraps
nothing, since plain CSS keeps the nesting instead of resolving it. All
`[measured]` against dart-sass 1.104.1 in both styles.

**The legacy `rgb()`/`hsl()` form choice closed the same day, for +28.** It was
the largest remaining family, and it came down to two rules in dart's
`_writeLegacyColor`, neither of which is what it looks like.

The first is when a channel counts as an integer, which decides whether a legacy
triple is written as numbers or as percentages. dart's `_asInt` is **exact**
(`rounded == number`) for CSS output and **fuzzy** for `meta.inspect` — the
reverse of what its own doc comment says, and the code wins: the same colour has
two spellings. `color.to-space(hsl(180, 60%, 50%, 0.4), rgb)` has channels
50.999999999999986, 203.99999999999997 and 204, so it is
`rgba(20%, 80%, 80%, 0.4)` as CSS and `rgba(51, 204, 204, 0.4)` under inspect.
sasso tested one fuzzy rule in both places, so the dust an hsl conversion leaves
behind was invisible where dart shows it. The fuzzy side needs BOTH clauses of
dart's `fuzzyEquals` — `|a - b| <= 1e-11` **and** `round(a * 1e11) ==
round(b * 1e11)` — because the second one rejects 19.999999999994987, which the
first accepts; that channel is a percentage even under inspect. The same
exactness governs `_canUseHex`, whose `[0, 256)` bound only inspect can observe,
since CSS output reroutes an out-of-gamut colour before the hex rule runs.

The second is that reroute. dart writes an out-of-gamut legacy colour as `hsl()`
— the one legacy form a browser does not clamp at parse time — and
`SassColor.isInGamut` measures every LINEAR channel against **its own space's**
bounds, fuzzily, with a polar hue always in gamut. So hsl and hwb are bounded to
`[0, 100]` on channels 1 and 2, not to the `[0, 255]` of the rgb conversion that
compressed output would otherwise write: `color.to-space(oklch(0.5 0.2 200),
hsl)` carries a 655% saturation over a shadow that is ordinary black, and
measuring the shadow printed `#000` where dart prints the hsl triple. sasso
measured the shadow in all three legacy spaces, so the whole family shared one
wrong test.

Making the first rule exact exposed a third divergence, in the arithmetic rather
than the serializer: dart builds a modified colour in the WORKING space through
`SassColor.forSpaceInternal`, which reduces a polar hue into `[0, 360)` *before*
the conversion back reads it, and sasso reduced it only afterwards. Only a
conversion can see the difference — `(390 % 360) / 360` is exactly `1/12` while
`(390 / 360) % 1` is an ulp short — and one ulp in a channel is the whole
difference between `color.complement(rgba(10, 20, 30, 0.4))` writing
`rgba(30, 20, 10, 0.4)`, as dart does, and writing a percentage triple. The lax
integrality test had been hiding it. No sass-spec case covers it either way, so
neither gate moved on that part; it is pinned by tests instead.

What did NOT need changing is the conversion arithmetic underneath: probing our
channel dust against dart's, channel by channel through
`color.channel(…) - <integer>` scaled by 1e14, came back identical to the last
bit, so only the two serializer tests and the one normalization order were at
fault. Compressed passing **14,009 → 14,037** (98.25% → **98.45%**) and expanded
**14,107 → 14,114**, the +7 being cases where exact integrality is what dart
writes in expanded output too (`color.adjust(red, $hue: 150, $whiteness: 20%,
$blackness: 40%, $alpha: -0.7)` is `rgba(20%, 60%, 40%, 0.3)`, not
`rgba(51, 153, 102, 0.3)`).

**The review pass found the same defect in six more places.** dart has ONE fuzzy
comparison, `fuzzyEquals`, and every classification in the legacy form choice is
built on it; sasso had transcribed it as a bare epsilon (`|a - b| < 1e-11`) in
some places and as 1e-9 or 1e-10 in others, each transcription dropping the 1e11
rounding clause that is half the comparison. Corrected, with the measurement
each one turns on:

- `_normalizeHue` matches `0` and any non-finite hue BEFORE applying the 180°
  a negative saturation or chroma asks for. Shifting first is a red-to-cyan bug:
  `color.change(hsl(120, 50%, 50%), $hue: 0, $saturation: -50%)` is
  `hsl(0, 50%, 50%)`, and `color.change(lch(50% 20 0), $chroma: -20)` keeps
  `0deg`.
- whether that saturation IS negative is `fuzzyLessThan(channel1, 0)`, so
  `-6e-12` inverts the hue (scaling by 1e11 rounds it to -1) where `-4e-13` does
  not.
- the in-gamut bound that decides whether a legacy color reroutes through
  `hsl()` was a 1e-9 window in the layer that builds a computed color, deciding
  the form before the serializer's own rules ever ran:
  `color.change(red, $red: 255.000000000006)` is `hsl(0, 100%, 50%)`, not `red`.
- the CSS named-color spelling is a MAP LOOKUP in dart (`namesByColor[rgb]`), so
  a hit needs `fuzzyHashCode` — the same 1e11 rounding — to agree on every
  channel: `color.change(red, $red: 254.9999999999)` is `rgb(100%, 0%, 0%)`.
- a hue is powerless when the saturation or chroma a conversion produced is
  `fuzzyEquals` to zero, and the lch/oklch test was ten times looser than the
  epsilon: `color.is-missing(color.to-space(lab(50% 0.00000000006 0), lch),
  "hue")` is false. The compressed writer derives its hsl bid the same way, and
  keeping that hue is what makes the rgb form the shorter one:
  `color.change(hsl(90, 50%, 50%), $saturation: -0.000000000006%)` compresses to
  `rgb(50%,50%,50%)`.
- the opacity test is `fuzzyEquals(color.alpha, 1)`, where sasso demanded
  `f64::EPSILON` in five places and 1e-11 in a sixth:
  `color.change(red, $alpha: 0.9999999999999)` is `red`, not an `rgba()` whose
  alpha prints as `1`.

Neither ratchet moves on any of it (`+0` expanded, `+0` compressed, nothing
gained and nothing lost in either style): no sass-spec case carries dust at the
boundary. They are pinned by integration and parity tests instead, and the point
of fixing them is that the boundary is where a wrong tolerance is INVISIBLE
until a real stylesheet lands on it.

One rule here is measured and **not** fixed: inspect mode writes numbers at full
precision, with no 10-decimal rounding at all (`_writeNumber` returns early when
`_inspect`), so dart's inspect of the colour above is
`rgba(3.9215686274500006%, 7.843137254899995%, 11.764705882349999%, 0.4)` where
sasso rounds each channel. That is a number-writer change with a blast radius
well beyond colours, and it is the only case in this family that still diverges.

style.

- The leading-zero family was MISDIAGNOSED by the triage above, and probing it
  is what corrected the reading: both leading-zero rules were already right and
  the arithmetic was not. dart's `_percentageOrUnitless` is
  `max * number.value / 100`, and the order of that multiplication is
  observable — `0.4 * -40 / 100` is exactly -0.16 where `-40 / 100 * 0.4` is
  -0.16000000000000003, which the rounding writer shortens, and a shortened
  spelling loses the leading zero the exact one keeps. `oklab(50% -40% -75%)`
  compresses to `oklab(.5 -0.16 -0.3)`. Gated on its own, with a per-case set
  diff: `[measured]` **+5**, none lost.
- An `@import`'s modifiers are ONE string, spelled by the parser and written
  verbatim by `visitCssImport`; the compressed media-query form belongs to
  `visitCssMediaRule`, which an `@import` never reaches. **5 cases.**
- In a plain-CSS `@function` body, dart keeps `result:` as verbatim source text
  (`_inPlainCssFunction` and a plain name equal to `result`) and parses every
  other declaration as SassScript — so only the SassScript one takes dart's
  OPTIONAL space, which is exactly the byte compressed output drops.
  **3 cases.**
- A private-use escape is for a READER, and `_tryPrivateUseCharacter` gives up
  when compressing: the character goes out as its own UTF-8 bytes, which is
  what earns the file the BOM. The quoted writer already did that; the unquoted
  one did not. **1 case**, `issue_1231`, byte-for-byte including the BOM.
- Making that writer style-aware exposed a fifth mechanism, in `meta.inspect`:
  dart inspects with `serializeValue(inspect: true)`, whose style is the DEFAULT
  one, so the string it hands back already carries `\e000` — long enough to
  change `string.length` (5, not 1) and ASCII enough to leave a compressed
  stylesheet with no BOM at all. No sass-spec case scores it.

The last three were verified case by case against live dart-sass rather than
gated one at a time; the ratchet confirms the total.

Two of the divergences the probes found are in BOTH styles, so no compressed
case could have scored them. dart's `_mediaQuery` writes the space that would
separate a media type from the next identifier BEFORE it learns that identifier
is `and`, then writes the whole `" and "` anyway — so an `@import` carrying
`print  and (…)` has TWO spaces where a real `@media` rule has one, and only an
`@import` can show it, since a media rule re-serializes from its parsed queries.
The `inspect` string above is the other. Both are pinned by parity tests.

**The fifteenth is now closed too**, by the node-kind flag the paragraph below
priced: compressed passing **14,051 → 14,052**, expanded `+0`, `pass` 11,559 →
11,560. `css/unknown_directive/name_interpolation` was the case, and the fact it
needed is one a NAME cannot carry: dart's PARSER picks the node class, so
`@media`/`@supports` are `CssMediaRule`/`CssSupportsRule` and everything else —
an unknown at-rule, `@font-face`, `@page`, `@keyframes`, a plain-CSS custom
`@function`, and any at-rule whose name arrived through interpolation — is a
generic `CssAtRule`. `@#{"media"} (a: 1)` merely spells itself `@media`. An
`AtRuleKind` field on `OutNode::AtRule` and `OutItem::NestedAtRule` now records
it; `OutItem::ChildlessAtRule` needs none, because a conditional group rule
always has a block (`@media (a: 1);` is "expected `{`" in both engines), so
anything childless is generic by construction. The two predicates in `emit.rs`
that used to match on the name take the kind instead, which is the whole fix:
33 live probes had already established that this one distinction accounts for
every form of the divergence — the compressed space at top level, childless,
bubbled out of a rule, nested inside a real `@media`, and childless inside a
rule, plus the empty-block survival in BOTH styles (`@#{"media"} screen {}`,
`@#{"media"} {}`, `@#{"supports"} (a: 1) {}`, and compressed
`@#{"media"} (a: 1) { /* c */ }`). The second half is what no sass-spec case
scores, in either style; parity and integration tests pin it. The gap between
the two ratchets is now 62 cases, all of them dual-ratchet-impossible.

The gate was verified to bite, not merely to pass: corrupting two digests drops
`passing` to 12,577 and `check_baseline.py --style compressed` exits non-zero
with `REGRESSION`. `spec/gen_compressed.py --show <case>` turns any digest
mismatch back into a side-by-side diff, since the manifest holds no text.

**#13 is the biggest user-facing number in this part, and it is not compiler
work.** `[read-from-code]` `CHANGELOG.md:419` states the gap verbatim:
"`import … from "sasso"` is always the wasm build." `native.mjs` already
implements the full modern API surface and loads the addon **synchronously** via
`createRequire`, so a sync auto-selecting entry needs no top-level await (which
would break `require(esm)` on Node 22+). The constraint is stronger than "a sync
entry is possible": `native.mjs` resolves the addon at *module-evaluation* time
and throws when none loads, and a static ESM import cannot be try/caught — so
refactoring the wrappers to take an already-resolved handle is **mandatory**,
not one option among several. Unlike the `node`-condition lever (E5 M-h), this
gain does not depend on the V8 tiering regime: `[read-from-code, docs:319]` the
2.8–3.0× was measured with the wasm arm at `--no-liftoff` steady state, so a
cold one-shot build's ratio is if anything larger. Watch two things:
`configure({arenaMiB})` is a no-op on native (`native.mjs:463`), and a skewed
addon must fall back **loudly** (#114's lesson).

### E5. Group 2 — one measurement away from being decidable

Each of these is blocked on a specific, cheap experiment. Do not write the diff
first.

**M-a. The `Value`-size control. Do this before E6's layout campaign, before
boxing `Error`, before anything.** `[read-from-code]` the tree carries
`const _: () = assert!(size_of::<Value>() <= 64)` at `src/value.rs:57` with a
comment saying "Bump this only with a deliberate measurement" — and **no
benchmark, gate or recorded A/B has ever read `size_of::<Value>()` in either
direction.** The experiment: add a `#[cfg(feature = "pad")] Pad([u8; 16])`
variant to grow `Value` 64 → 80 and measure the **regression** on
`large`/`units`/`colors`, interleaved, one afternoon. If +25% bytes measures
under 0.5%, then −37% bytes cannot be worth −1.5 to −3.0% and the whole layout
campaign is dead for the cost of one afternoon. If it measures 1.5%, the
campaign is the headline it claims to be. Metric reproducibility is 0.003%
`[measured, D5]`, so this resolves cleanly.

**M-b. Box `Error` in the 77 `Result<(), Error>` signatures only.**
`[measured, replica, rustc 1.98.1 aarch64]` `Error` is 72 bytes, **larger than
`Value`'s 64**; `Result<Value64, Error>` is 72; **`Result<Value40, Error>` is 72
too** — so shrinking `Value` alone buys *exactly zero* on all 157 return slots.
`Result<Value64, Box<Error>>` is 64; `Result<Value40, Box<Error>>` is 40 (the
shrunken `Value`'s own niche absorbs the tag). And the half nobody wrote down:
**`Result<(), Error>` is 72 against `Result<(), Box<Error>>` at 8** — an sret
stack slot becoming a register return, on 77 signatures including
`Evaluator::exec` at `mod.rs:2828` (`[measured, D4]` 4.87% / 3.79% self cost).
That is a calling-convention change, qualitatively bigger than anything on the
`Result<Value, _>` side, where 72 → 64 does **not** change the return mechanism
(both exceed 16 bytes, both use sret on aarch64 and x86_64) — what 64 buys there
is stack frame plus a dropped tag store. Measure the `Result<(), _>` half
**alone** first: it is 77 sites instead of `[measured, grep]` 734 `Err(` plus 52
`map_err`/`ok_or_else`, and it carries most of the gain. Safety confirmed: `Err`
is **not** control flow — `@return` propagates as `Ok(Some(v))` at
`control_flow.rs:509` — so boxing puts no allocation on any success path. Hard
constraint: `pub message`/`line`/`col` are read by `ffi/src/lib.rs:657`,
`napi/src/lib.rs:515-538` and `wasm/src/lib.rs:211-236`; the boundary unbox at
`lib.rs:380`/`:434` must keep `Error`'s shape exactly.

**M-c. Count `push_num` calls.** `[measured, D4]` the row is 10.47% of `large` ≈
10.7M instructions; `[measured]` 2026-09-18, `large.scss`'s output holds 19,125
number tokens (12,875 fractional, 6,250 integer) with a fraction-digit histogram
peaking at 10dp:6,500 — which independently reproduces the audit's "264 numbers
>10 decimals per 1,000 output lines". The audit's calibrated model (~450
instructions per long fraction, ~40 per other) gives ~3.3M for that mix. **The
two disagree by ~3×.** Either `push_num` is called ~3× more often than the
output has numbers (plausible: colour channels, length comparisons, inspect
paths, discarded candidates), or one figure is wrong. A one-line counter settles
it, and **every expected gain in the number dimension depends on the answer.**
Land it before any formatter work.

**M-d. Is dropping `push_num`'s spelling scan a real lever or a corpus
property?** The mechanism is sound and provable: `[read-from-code]` `format64`
never emits exponent form, so `rust.contains('e')` at `value.rs:2896` is a
**compile-time false** — a per-number memchr over a constant answer;
`sig == digits.len()` holds on the non-integer path because `push_num` returns
early when `n.fract() == 0.0`, forcing `exponent < 0`; and both `find('.')`
scans are derivable as `point = digit_len + exponent`.
`[measured, otool on the shipped 0.17.0 binary]` `push_num` is one
1,561-instruction out-of-line function with **four** out-of-line
`CharSearcher::next_match` calls and a `memchr_aligned` — real calls with real
prologues — and the `skip_while` loop is 8 instructions per ASCII byte.
`[estimated]` 1.5–2.5% of `large`. **But it is a strict subset of audit lever
4.5**, which `[measured]` was −4.17%/−7.40% on `large` and **0.0% ±0.25% on
bootstrap, bulma, tabler, govuk-frontend and font-awesome**, and which A4 lists
under "Do not land these". The corpus ratio is the whole story: 264 long numbers
per 1,000 output lines on `large` against bootstrap's 39, tabler's 22, govuk's
10, **font-awesome's 0**. Decide it by measuring the subset on a real framework.
If it reads 0.00% there, land it for its 1.5–2.5% on number-dense input and
**say plainly that it is a corpus property.** Fold in the two remaining tail
re-reads — `&out[start..] == "-0"` and `starts_with("0.")` plus
`out.remove(start)`, both decidable from the sign bit and the exponent metadata
the same change is already threading out, and `[measured, audit 4.6]` the
ancestor of that `remove()` was −1.10% standalone on a compressed compile of
`large`. Do **not** also reorder the frac>11 test: it is worth ~0 once the digit
count is free, and it cannot be done without it anyway.

**M-e. Byte-only selector validation plus the fused prescan, as ONE change.**
These are the same loop; their gains are not additive, and costing them
separately triple-counts (the fused prescan also shares the resolved-selector
pass with E4 #3). Joint `[estimated]` ~0.8–1.4% of `large`; treat #2, #3 and
this as one family worth ~2–3%, not five changes worth 0.5% each.
`[read-from-code]` all ten per-rule traversals exist, and D4's "~0.5%" covers
only three of them — D4's table cuts off at ~2%, so the scans inside
`validate_selector`, `resolve_selectors_opt` and `normalize_selector_owned` are
invisible in it entirely. `[measured, asm]` the dominant fixed cost of
`CharBuf::of` is **not** the 256-byte zero-fill (~17 instructions) but the UTF-8
decode loop at **12 retired instructions per ASCII character**, unvectorized at
both −O2 and −O3 — so an 8-char selector costs ~113 instructions just to
materialize. The blocking prerequisite is not a benchmark, it is **the oracle
plus the missing corpus**: rebuild the check build asserting old == new `Result`
on every call across the full suite, and add the >64-char selector-part shape,
because `[measured, commit 8753bd3]` a 300-rule long-selector sheet caught two
shapes of the `CharBuf` change regressing **+7.541%** and +0.598% while
`large.scss` showed both as wins — and that sheet is scratch, not in
`bench/corpus/`. Every lever here rewrites exactly those scanners.

**M-f. `declared_css` deferred to emit** — `[estimated]` 0.5–0.7% of `large`,
and it is **the only item in the number/allocator dimension whose gain scales
with declaration count rather than number density**, so unlike M-d it should not
collapse on bootstrap. `[measured]` 13,200 declaration values in `large.scss`'s
output, each paying a `String::from(buf.as_str())` that emit then copies again.
The blocking question is not performance, it is whether the predicate can be
written: `[read-from-code]` `mod.rs:3449-3452` drops the whole declaration when
`vstr.is_empty()` ("an empty unquoted string, an all-null list"), so deferring
means either serializing eagerly anyway (defeating the lever) or writing a
second, parity-critical `serializes_to_nothing(&Value)` — a duplicate of a dart
rule in a second place, which is exactly what 4.5's ship conditions said not to
do. Also `OutItem::Decl.value` has three other producers carrying *text*
(`mod.rs:3488` custom property, `plain_css.rs:504`/`:525`, `at_rules.rs:883`),
so the field becomes an enum with a branch in both emitters, and only the
non-custom arm can be deferred. Prototype the compressed emitter, answer the
predicate question, then decide.

**M-g. The number-format memo cache's hit rate is measured on the wrong key
space.** `push_num` is genuinely pure in `(bits, compressed)`
`[read-from-code]`, and the repetition is real (`[measured]` 19,125 tokens over
**263 distinct spellings**, top-15 = 49.3%). But the 95.99% / 87.98% / 67.25%
simulation was derived from the **compiled CSS**, i.e. from spellings already
rounded to 10 decimals — and rounding is many-to-one, so it collapsed distinct
cache keys into one. Those hit rates are an **upper bound of unknown
tightness**, and the distinct pre-round key count cannot be obtained from the
output at all; it needs a counting print inside `push_num` (fold into M-c). Two
further reasons for caution: `[measured, disassembly]` every macOS
`thread_local` touch is an indirect call through `_tlv_get_addr`, which the
~10–15-instruction hit estimate omits; and a ~34 KB table touched near-randomly
is an L1-hostile addition that costs **cycles, not instructions** — the
instruction metric will over-credit it, which is precisely why E2 comes first.
On real sheets the audit's calibrated model caps the entire number path at
0.3–0.5M instructions, so no formatting cache can be worth >0.05% there.

**M-h. The `node` export condition against `opt-level = "s"`.**
`[measured, three_way.md 2026-06-13]` `-Oz` 27 ms against speed 12 ms (2.25×) on
the large corpus; `[measured, docs:250-252]` 18.0 against 15.2 ms (1.18×) on the
36-file modular corpus. **But `[read-from-code, docs:283-288]` "−O3 vs −Oz
module differences measure at parity" in short-lived default-tiering Node
processes, and F2's 2× "only exists" in steady state.** So the lever is large
for a dev server or watch mode and **~0 for a one-shot build — and there
slightly negative**, because `[measured]` 2026-09-18 the bigger module costs
~+0.6 ms of decode per process (1.79–1.95 ms against 1.23–1.25 ms). The
competing move nobody tried: `opt-level = "s"` (not `"z"`) for the *default*
module, which helps **every** consumer including browsers with no packaging
change at all — `"z"` pins the inline threshold near zero and disables
unrolling, and `"s"` is the usual knee. Measure both arms against each other
rather than assuming the manifest edit. Packaging traps if you take the `node`
route: the key must sit **before** `import` inside the `"."` object or it never
matches for ESM, and `main`/`module` still point at `sasso.mjs` for tools that
ignore `exports`.

**M-i. The wasm arena is probably exhausted on any large-output compile, and
nothing reports it.** `[read-from-code]` `WASM_DEFAULT_ARENA_SIZE` is 32 MiB,
sized by a prose comment ("peaks around 25 MiB") that nothing asserts; on
exhaustion every allocation falls to dlmalloc **and** the in-place tail-realloc
fast path stops applying to growing buffers, so each doubling of a multi-MB
`Vec` becomes malloc + memcpy. The binding quantity is **total bytes bumped**,
not peak live: `[measured, A5]` 44× byte amplification × 521 KB of output ≈ 23
MB, which is exactly where the comment's 25 MiB came from — so a compile
emitting 40× that output needs order 1 GiB of bump and exhausts within the first
few percent. The "post-exhaustion tail" is then nearly the whole compile. Two
honest counterweights: the 25 MiB figure predates Part D's −73.6% allocation cut
and has never been re-measured, and the borrowed 1.6× arena win was against
native malloc, not dlmalloc. **The first task is not a fix.** Add an exhaustion
counter (`arena.rs:492-494` falls through silently; `reserve_failed` and
`registry_full` are tracked, a bump failure is not) and a big-output corpus —
the largest committed source is `bench/corpus/gate` at 196 KB total. Then the
cheap half: `[measured, grep]` `SASSO_WASM_ARENA_MB` is never set by `build.sh`
or any workflow, no shipped entry calls `configure({arenaMiB})`, and the only
documentation of the knob — `wasm/npm/README.md:327-328` — recommends
**lowering** it to 16 MiB. While in that file, note `[read-from-code]` the
realloc fallback never forwards to `System.realloc`: it does alloc-new + copy +
dealloc even for a pointer `in_any_arena` has already classified as *not*
arena-owned, which is the exact post-exhaustion path and also every `Vec` growth
outside a scope.

**M-j. `Color`'s `modern` field behind an `Rc`.** The mechanism is right and
safe — `[read-from-code]` all 4 writes replace the whole field, all 26 `.modern`
uses are borrows, no `as_mut`, no `take()`; `[measured]` `ModernColor` is 72 and
`Color` is 56 either way, so nothing shifts. And `[measured, commit 8a1804f]`
the identical change to `Color`'s *other* heap field measured −1.121% on `large`
and −2.68% on `colors`. **But `[measured, grep]` there is not one modern-tagged
colour in any corpus in the tree**: `hsl(`/`hwb()` are the only legacy-syntax
constructors that attach a tag, `hsl(` appears 6 times in all of `bench/corpus`,
every one a one-shot declaration value never bound to a variable, and the
`colors` benchmark's `color.adjust`/`rgba`/`mix` over a hex literal takes the
legacy path while `make_modern_in` leaves `modern: None` for in-gamut rgb. So
D3's standing rule — an allocation-count win ships only after the
marginal-instruction A/B agrees — **cannot be satisfied**, and this reads 0.00%
on every corpus and on the CodSpeed gate. Add the oklch/lab/hwb corpus **first,
in its own commit**, or park it. Same story for the `assign` key allocation

three-line change with a measured shape and no in-tree corpus that exercises it.

### E6. Group 3 — structural: a campaign, not a patch

**S-a. The `Value` layout campaign.** Every size figure was independently
reproduced `[measured, replica, rustc 1.98.1 aarch64]`: `Units` 24, `Number` 32,
`Color` 56, `Slash(Number, String)` 56, `List` 48, `CalcNode` 48, `SassFunction`
48 → `Value` 64; the proposed shape reaches **40**; `(String, Value)` 88 → 64,
`(Value, Value)` 128 → 80. **40 is the floor** — `Number` is 32 because `Units`
is 24 with no niche, and boxing the most-constructed variant in the tree to save
24 bytes of move is not a trade. Four things to get right:

1. **Run M-a first.** The pad control can kill this for one afternoon's work.
2. **The entire size win is gated on the single most expensive sub-change.**
   `keywords → Rc` takes `List` 48 → 32 and `Slash → Rc<str>` takes it 56 → 48,
   but `Color`'s 56 still binds, so `Value` stays **64**. `[measured]` a replica
   with `Slash`, `Calc` and `Function` boxed and `keywords` behind an `Rc`, with
   `Color` left inline, is still 64 bytes. Anyone who reads D4's "shrinking
   `Value` … is the lever" as one move will land a no-op and conclude the lever
   is dead.
3. **Measure the cheaper rung first.** Fold `repr` and `modern` into one
   `Option<Box<ColorExtra>>`: `Color` 56 → 40 with **no `Rc` on the construction
   path** (both fields are already `None` on the common legacy path, so the
   common case pays nothing). With `Slash` and boxed `Calc`/`Function`, max
   payload is 40 and `Value` is 48 — strictly smaller and strictly cheaper than
   the 64 → 40 diff. Note the tension: `[read-from-code]` putting the hot
   authored spelling behind an allocation partly undoes `8a1804f`.
4. **Three of the five sub-changes add an allocation on a hot *construction*
   path, which is the exact trade D3 measured and lost.** `Color(Rc<Color>)`
   puts an `Rc::new` on every computed colour, and `large.scss` constructs each
   colour about once and serializes it once, so that arm is `[estimated]` a wash
   or worse there; `Calc(Box<CalcNode>)` runs against batch 15 (#106,
   `777a385`), which went the *other* way and serialized a calculation into the
   caller's buffer. **Bisect the five arms separately** — D3's bisect is the
   precedent for why a bundle hides a regression — and keep `longsel` as the
   control that must read 0.000%.

**Strike the memmove citation.** `[read-from-code]`
`bench/perf_audit_2026-09-15.md:152` reports memmove 10.2–10.4% as a share of
**wall samples**, not instructions; the same row puts realloc copy volume at
1.47 MB/compile (~15 µs), i.e. most of it is `String`/`Vec` plumbing; and the
row is from the **pre-campaign** tree (387,321 allocations, 153.2M
instructions). The current memmove share is unmeasured. The line that actually
caps the claim sits immediately above it: `Value` clone + drop at 4.05% of wall
(2.05 + 2.00). Cutting 64 → 40 removes ~37% of the bytes but not the
discriminant switch or the per-variant refcount work, so the clone-side ceiling
is `[estimated]` ~1.0–1.5% of wall, not 3%.

**S-b. The `@extend` residue — the one place D2's arithmetic is false.**
`[read-from-code, REFACTOR_PLAN.md:30-37, :100-134]` the render strings
"overflow the 2 GiB arena → individually malloc'd **AND** free'd", and
`[measured]` "the malloc/free family is ~49% of extend-path self-time".
Everywhere else in this program an allocation is a pointer bump; here it is a
real malloc. What remains:

- `[read-from-code]` `extend_to_fixpoint_inner:3763` builds a `String` **per
  product** via `c.render()` for an `FxHashSet<String>`, while the fold path
  keys on `Hashed<Complex>` with a comment explaining exactly why. The same
  `FxHashSet<String>` + render shape recurs at `:3903`, `:4058`, `:4257`,
  `:4823`, `:5038`. **Do not naively convert them**: the set *retains* its key,
  a retained `Complex` is a deep `Vec`-of-`Vec`-of-`String` clone, and
  `rendered.len()` is load-bearing three lines down for the

- `[read-from-code]` `extend_selector_list:6604-6606` does `v.join(", ")` then
  `crate::selector::parse_list(&joined)` **per rule**, on every sheet with a

  character and the extender immediately re-parses them into the typed model it
  wanted all along. `RuleSelectors::Parsed` already exists as a variant and the
  comment at `:6598` says it is "not produced today". **This is the structural
  selector lever for `@extend`-bearing sheets and no prior pass proposed it.**
- `[read-from-code]` `collect_extenders:4287` is still a linear
  `for ext in extensions` with a `Simple` compare per entry. This is audit
  sub-lever (3), the "target-simple index", recorded as unbuilt — and it is
  **still** unbuilt on *both* paths. `complex_may_match_targets`/`batch_targets`
  is a *different* mechanism (a complex-side prefilter) that
  `[measured, git log -S]` has existed since `c84e9a4`, 2026-06-13, three months
  before the audit; the two were conflated. Porting the prefilter to the
  one-shot path is not sub-lever (3), and **A2's −48.4%/−29.4% are not its
  ceiling** — the audit says in terms "Sub-lever (3) … is unbuilt and
  unmeasured. Do not land it on this evidence." Selectivity also cuts against
  the port: on the fold path each batch has one target so the filter is sharp,

  registry, so the target set is at its **maximum** and the filter at its most
  permissive. **First measurement: instrument the arm split and the prefilter
  hit rate on `extend_heavy` plus two real frameworks.** If the one-shot arm is

  asymmetry: the fold path gates `consume_extend_work()` *behind* `can_match`;
  keeping it unconditional is a different trajectory, and `apply_extends`
  documents the trajectory as output-affecting.

**S-c. PGO, with a reproducibility policy decided first.** The program is the
canonical beneficiary — `[read-from-code, D4]` the top symbols are large match
dispatchers whose branch weights LLVM guesses — and the training set exists and
is verified (`[read-from-code]` `codspeed.yml:23-24` runs

`[estimated]` **1–5% on aarch64-apple-darwin and 3–10% on x86_64** — not 5–20%

and block layout is what PGO monetises. And of the `[read-from-code]` seven dist
targets, at least four (both musl triples, aarch64-linux-gnu, windows-msvc)
cannot run an instrumented binary on their own build runner — so a committed or
cross-target profile is **the design, not one of two options**. A PGO binary is
not bit-reproducible from source alone, which cuts against Nix, ports and
Homebrew-from-source. **Gate the whole idea on the topdown result (E2 step 3):
if retiring dominates, do not open this.** Prove it locally on one target before
touching CI.

**S-d. Hot/cold split `exec`'s 29 arms.** `[read-from-code]` `Stmt::Decl` (arm
3) and `Stmt::Rule` (arm 6) are the two arms a large stylesheet executes
overwhelmingly, interleaved through ~300 lines with `For` (~27 lines), `Each`
(~23), `Include` (~35) and a dozen more. Outline the cold arms with
`#[inline(never)]`. **This is the reference example of a lever the current
metric cannot score**: it moves instructions by ~zero (it may add a call), so it
reads 0.00% on the metric of record *and* on the CodSpeed headline, and its
entire effect is on I-cache footprint. **Strictly conditional on the topdown
split showing a frontend or bad-speculation component; if it says
retiring-bound, do not build it.** Note what it is *not*: reordering match arms
by frequency does nothing, because Rust lowers a dense enum match to a jump
table on the discriminant — source order does not change the dispatch.
Regression risk runs the other way (outlining costs instructions on paths that
are not cold on a control-flow- or deprecation-dense corpus); `control_flow` and
`legacy_deprecations_with_url_silent` are the benchmarks that catch it.

**S-e. Gate the artifacts, and fix the memory metric.** `[measured, grep]` no
`wc -c`, `size`, `hyperfine` or `--loop` anywhere in `.github/workflows/` —
there is no size or throughput gate on the binary, the addon or the four wasm
modules. **Every lever in the build dimension is output-identical by
construction, so sass-spec's ratchet — this project's strongest gate — says
nothing about any of them.** The two measurements above are the argument: −1.28%
and +0.2% are both completely invisible to every check CI runs. Land in this
order:

1. a size ratchet on the four `.wasm` files with a committed baseline, which is
   noise-free and has an existing home at `wasm/test.mjs:401-435`;
2. pin binaryen — `[read-from-code]` unpinned in **four** places (`ci.yml:76`,
   `ci.yml:114`, `release-wasm.yml:119` which also `brew install`s,
   `release-wasm.yml:161`), so the optimiser producing the shipped artifact is
   whatever the runner image ships that week, and `build.sh` enables a
   **narrower** feature set (`bulk-memory`, `nontrapping-float-to-int`,
   `sign-ext`) than `[measured]` rustc emits for the target (`multivalue`,
   `reference-types` also on) — the build works only because CI's binaryen
   defaults those on;
3. throughput as a **report, not a failure**, per B0/B2's own argument.

A corpus only works as a gate if it **amplifies**:
`gate/legacy_deprecations.scss` amplifies A1 ~3× (−48.3% against −17.4%), and
with a 2–3% threshold a 1.7% lever is below the gate even with a dedicated
