## The blocker: gRPC 404 through Traefik (EVIDENCE, not theory)
- Direct to pod (port-forward, h2c prior-knowledge):
  `POST /management.ManagementService/GetServerKey` →
  `HTTP/2 200, content-type: application/grpc, grpc-status: 2 (EOF on
  empty body = method EXISTS and parsed the request)`. Server is FINE.
- Same request through Traefik (`https://netbird-mgmt.toyvo.dev/...`):
  `HTTP/2 404, text/plain` WITH Traefik secure-headers (HSTS etc.).
  Middlewares ran → route MATCHED → backend (or Traefik itself) 404'd.
- Conclusion: Traefik is NOT speaking h2c to the backend despite
  `traefik.ingress.kubernetes.io/service.serversscheme: h2c` on the
  live Ingress (verified present via kubectl). It forwards HTTP/1.1,
  hitting Go's plain-HTTP mux (no REST route for gRPC paths) → 404.
- Tried: h2c annotation (deployed, verified on object, no effect);
  downgrading 0.83.1→0.82.0 to match nixpkgs client (no effect —
  correctly ruled OUT version skew; both sides 0.82.0 now).
- Ruled out: DNS (grey, resolves home IP, TCP connects), TLS (valid LE
  cert, ALPN negotiates), duplicate routers (single Ingress, no edge
  route), version skew (aligned), secrets (all present).

## Most likely next steps (in order)

   Ingresses at all (may have moved to IngressRoute-only or require the
   Service port named e.g. `h2c`). Check Traefik docs for v3.7.
2. Alternative: switch the management Ingress to an IngressRoute with
   explicit `serversTransport` + h2c scheme (CRD gives full control;
   proven pattern from the euro-office backend-TLS work).
3. Alternative: bypass Traefik for agent gRPC — NodePort the management
   gRPC port directly (agents point at `https://10.1.0.3:3xxxx`? No —

4. Nuclear: put a tiny gRPC-aware reverse proxy (e.g. a second Traefik
   with explicit h2c transport, or envoy) in front of management.
5. Dashboard SPA bug (separate): never initiates OIDC (no authorize
