# OmniRoute Upstream Admission Interruptions

## Symptom

OpenCode flows appeared as `interrupted` immediately after a model request started.

## Cause

OpenCode displayed flows as `interrupted` because OmniRoute relayed the upstream error `Chat admission capacity is temporarily unavailable. Retry shortly.`

This message is **not generated by OmniRoute**. Verified: the string is absent from OmniRoute 3.8.49 source (local checkout matches the deployed image). OmniRoute reads it from the upstream provider response body via `parseUpstreamError` (`open-sse/handlers/chatCore.ts:3001-3012`) and relays it; the Vercel AI SDK wraps it as `AI_APICallError`.

The upstream is a set of **third-party OAuth relay gateways**, confirmed by the provider pool and error distribution:

- The exact strings (`Chat admission capacity is temporarily unavailable`, `Structurally heavy chat request capacity is busy`) are absent from OmniRoute 3.8.49 source entirely, so they are relayed verbatim from upstream HTTP responses.
- High-volume models route through OAuth subscription relays: `codex` (gpt-5.6-sol/terra/luna) and `agy` (~20 pooled Claude/Gemini OAuth accounts). These relays impose their own shared-pool admission control and return the capacity message when saturated.
- Direct API-key providers do not exhibit it: `zai` ("Ata Coding Plan") produced only ~45 admission errors vs thousands for `codex` and the `agy`-served Claude combos.
- `claude` direct provider shows `requestCount: 0`; all Claude traffic actually flows through `agy` (every Claude combo falls back to `agy/claude-opus-4-6-thinking`, `agy/claude-sonnet-4-6`).
- Several `agy` accounts report `tokenStatus: "expiring"`; as tokens expire the effective pool shrinks and admission pressure rises.

This is upstream of and outside OmniRoute's control.

## Resolution

The heap ceiling bump is hygiene, not the fix for these interruptions:

```env
OMNIROUTE_MEMORY_MB=2048
NODE_OPTIONS=--max-old-space-size=2048
```

`omniroute.docker-compose.yaml` requires both values from the Coolify environment and passes them to `omniroute-backend`. This removed the secondary local heap trigger but did not stop upstream admission rejections.

To address the actual upstream admission capacity:

1. Confirmed: high-volume traffic (Codex, Claude) routes through OAuth relay gateways whose shared-pool admission control rejects bursts. Prefer **direct API-key providers** (e.g. the existing `zai` "Ata Coding Plan") in fallback chains — they do not exhibit the admission problem.
2. Reduce request bursts from OpenCode. OpenCode spawns parallel subagents with no concurrency cap; a burst fans out to every fallback model in the same second and saturates the relay admission queue. Lower parallel subagent count / `subagent_depth`.
3. Raise OmniRoute `requestQueue.maxWaitMs` (Settings → Resilience) so a transient upstream 503 waits and retries instead of fast-failing to `interrupted`.
4. Refresh/rotate the `expiring` `agy` accounts to keep relay pool capacity up, or add more direct API-key providers.

## Guardrails

- Do not increase request concurrency to address this condition; concurrent large compactions raise local heap pressure and bursts saturate the upstream admission queue.
- Keep `OMNIROUTE_CHAT_HEAP_SHED_RATIO` and the `heapPressure.ts` ratio at their defaults unless memory behavior is measured. Raising them trades graceful rejection for process-wide OOM risk.
- Rotate and store `OMNIROUTE_WS_BRIDGE_SECRET` only in Coolify environment variables; never commit its value.

## Verification

After deployment, confirm OpenCode requests no longer receive admission-capacity errors in OmniRoute logs and monitor the OmniRoute heap ratio during concurrent compactions.
